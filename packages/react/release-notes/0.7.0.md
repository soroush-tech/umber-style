## @umber-style/react@0.7.0

A page of server components works under a strict nonce policy on Next.js, on its first load, with JavaScript off, after a client-side navigation and while it streams, and a style registry for the Next.js App Router writes the styles of a request in the head and between the pieces of the stream; the style functions of an element share one argument, and the theme cannot be written in development; a client component that reads a token below a provider of server components gets the same class on the server and in the browser.
([#66](https://github.com/soroush-tech/umber-style/issues/66), [#68](https://github.com/soroush-tech/umber-style/issues/68), [#69](https://github.com/soroush-tech/umber-style/issues/69), [#70](https://github.com/soroush-tech/umber-style/issues/70), [#71](https://github.com/soroush-tech/umber-style/issues/71))

### Added

- **`StyleRegistry`** of the new entry `@umber-style/react/next`: added once around the page in the root layout of the App Router, it collects the styles of each request (of server components in a request with a nonce, and of client components: the classes, the theme and the global rules of each style, or every rule of a `cache` made for the request) and writes them with `useServerInsertedHTML`, each once, with the nonce they came with, in the head for the first piece of the stream and at the top of the body before each later piece. No style element is among the elements of the page, so with JavaScript off nothing shifts `:first-child`, `:nth-child` or `+`, every rule comes before the first element that uses it, and a class first shown in a `Suspense` fallback no longer has a frame without its rule when the content replaces it. A client-side navigation writes its rules after the last style element of the engine, in document order. With a `cache` it writes what the registry an app writes by hand writes, so an app needs none. In a request with no nonce the server components keep the elements React hoists; without the registry nothing changes.
  ([#70](https://github.com/soroush-tech/umber-style/issues/70))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/cache-and-server.md#a-registry-for-the-nextjs-app-router)

### Changed

- In a request that has a nonce, from a source registered with `setNonceSource` or fixed on the cache (`createCache({ key, nonce })`, `configure({ nonce })`, with no source at all), the server components build sends no `<style href precedence>` element, which React merged into one element with no nonce where the framework gives React none (Next.js 16.4.6). A styled component, `Global`, a provider with `isRoot` and the browser part of a provider render a `<style nonce>` in place in the first HTML instead, which the policy lets in with JavaScript off; at hydration it hands its rules to elements of the head that carry the document's nonce and leaves its place, with no change of any computed style. After a client-side navigation the rules are written into the head with the document's nonce, so the browser gets no element with the nonce of the navigation's request. The text written comes from the app's own payload only, and an element the policy refused never counts as present, so an injected element stays refused. A request with no nonce at all gets the elements of 0.6.0 unchanged.
  ([#66](https://github.com/soroush-tech/umber-style/issues/66))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/server-rendering.md#server-components-a-nonce-for-each-request)
- The style elements of a class string are remembered for each cache and nonce, and a render of the string again takes the same list while each class has the rules and animations it had: a class let go and written again, and a class the cache did not have and has now, make a new list. The list is at most 10,000 strings for each cache and nonce (then it is emptied) and goes with the cache. It is the list of the classic server render of the browser build and of `ThemeProvider`; the server components build makes its elements from the texts, for the nonce of each request, and is as before. The elements are the same, with the same keys and props.
- A styled component reads its props with `Object.keys` instead of `Object.entries`, so a render makes no array of pairs for each element, in the same order. In a warm `renderToString` of the design system's every-component page the three changes of this release and of `@umber-style/core` took it from 5.0 ms to 4.2 ms and from 6.4 MB to 5.1 MB allocated (the fastest of 7 rounds); the HTML is byte for byte the same.
- **Breaking, in development: the style functions of an element share one argument, frozen in development** (`@umber-style/core`). A styled component gives its functions one object in a render, `{ ...props, theme }`, made in the render and never kept, where each function got a copy of its own. With the development checks, a function that assigns or deletes a key of it throws:
  `[umber] A style function of "box-root" threw a TypeError of a write into a frozen object: Cannot define property tone, object is not extensible. In development the argument of a style function is frozen: it is one object, the props with the theme, shared by the style functions of the element in a render. Copy the argument before changing it: const own = { ...props }.`
  In production nothing is frozen, and a change to the argument is seen by the later functions of the same element. What to do: copy the argument before changing it, `const own = { ...props }`. On the design system's every-component page, a warm `renderToString` took 3.92 ms where it took 4.15 (fastest), 4.45 where it took 4.64 (median), and allocated 4.7 MB where it allocated 5.0 (the method is in the notes of `@umber-style/core`); the HTML is byte for byte the same.
  ([#69](https://github.com/soroush-tech/umber-style/issues/69))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/writing-styles.md#object-styles-and-function-styles)
- **Breaking, in development: the theme a function gets cannot be written.** With the development checks, a write at any level into the theme given to a style function, a function sheet of `StyleSheet.create`, a function of `keyframes`, of `globalStyles` (for `Global`) or the function given to `ThemeProvider` as its `theme` (in both builds: in the server components build it is the base theme, the same object for every request) throws, naming the path and the function:
  `[umber] theme.palette.text is set by a function of "ThemeProvider". The theme is one object, shared by every render and every request, so a change to it reaches all of them: never change it. Build a new object instead, such as { ...theme.palette, text: value }.`
  What to do: never write into the theme; build a new object instead. In production nothing changes. In development, a provider function that returns parts of the theme above as they are passes those parts on guarded: they read the same and refuse a write.
  ([#69](https://github.com/soroush-tech/umber-style/issues/69))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/themes.md#the-theme-a-function-gets-is-shared-never-change-it)

### Fixed

- A client component whose style reads a token, below a `ThemeProvider` of a server component, made its class with no value for the token where its style module was not loaded yet when the provider rendered: on the first request of a server, at hydration, and after a client-side navigation to its page. Its class then differed from the one a warm server sent (so the browser wrote a rule of its own), and after a navigation the token had no value. The provider merges its theme over the base theme of the client build, which a process has only once a style of that prefix is loaded; now a theme given with no base theme under it is merged over the base theme of the style that reads it, so the class and its rule are the same on the first request, on a later one, at hydration and after a navigation. Where the style was loaded first, nothing changes.
  ([#71](https://github.com/soroush-tech/umber-style/issues/71))
- Under a strict nonce policy with a nonce for each request, the client build wrote every class new to the document (after a client-side navigation, a change of props or state, a component that mounts after a click) into a style element with no nonce, which the policy refused: its style has no nonce, and a nonce for each request cannot be put in the bundle. The engine's cache now gives its elements the nonce of the page when it has none (`@umber-style/core`), the one `NonceStyles` writes the head with too: they read it by one definition. A nonce given to the style wins, and a page with no nonce is as before. With the development checks, a refused element is warned about once.
  ([#71](https://github.com/soroush-tech/umber-style/issues/71))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/server-rendering.md#content-security-policy)

### Packaging

- Depends on `@umber-style/core` `^0.7.0`, `@umber-style/is-prop-valid` `^0.7.0` (it was `^0.6.0`).
- One more client module (`'use client'`), which the server build reaches by reference, as it reaches the browser part of `ThemeProvider` and of `Global`.
- A new entry, `@umber-style/react/next` (`dist/next.mjs`, `dist/next.cjs` and their declarations), the one file of the package that imports `next`. `next` `^16.4.6` is an optional peer dependency (`peerDependenciesMeta`): the versions tested, from 16.4.6, before 17: an app that does not import the entry needs none.
  ([#70](https://github.com/soroush-tech/umber-style/issues/70))
