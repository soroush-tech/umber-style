## @umber-style/core@0.7.0

A release for the version that every package of the family carries, a faster value repair, one argument for the style functions of an element, a theme that cannot be written in development, and the browser's style elements under a strict nonce policy.
([#68](https://github.com/soroush-tech/umber-style/issues/68), [#69](https://github.com/soroush-tech/umber-style/issues/69), [#71](https://github.com/soroush-tech/umber-style/issues/71))

### Added

- What the React Native binding shares with the engine for its development checks (**`createThemeGuard`** and **`callCheckedStyle`**, in the entry **`@umber-style/core/internal`**): a theme wrapped so that a write at any level throws, naming the path, and a style function called with its frozen argument, a write into it thrown again with the name of the component. **`engine.guardTheme(theme, label)`** gives the theme as a function of app code gets it, and **`resolveThemeInput`** takes the guard as a third argument, for the function of a provider.
  ([#69](https://github.com/soroush-tech/umber-style/issues/69))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/plain-javascript.md#everything-umber-stylecore-exports)

### Changed

- A cache with `hasValueRepair` remembers the text that each value was repaired to, and takes it again when it compiles that value again, which a render over a warm cache does for every class it names. The memo is the cache's, holds up to 10,000 values (then it is emptied), is emptied when the engine registers the values of a theme, so a changed token is repaired again, and is not used when a development check reports what repair leaves, so every report is still given. A reference that no suffix can follow is passed at once, and the text of a report is made only when there is a report to give it to. The text written is the same. In a warm `renderToString` of the design system's every-component page (82 components, `hasValueRepair` on) the page took 4.2 ms where it took 5.0 (the fastest of 7 rounds, with the two changes of `@umber-style/react` below) and allocated 5.1 MB where it allocated 6.4 MB; the home page took 73 us where it took 86.
  ([#68](https://github.com/soroush-tech/umber-style/issues/68))
- **Breaking, in development: the style functions of an element share one argument, frozen in development.** Each style function got a copy of its own of the props and the theme (`{ ...props, theme }`), made for each function in each render. The functions of an element now get one object in a render, made in the render and never kept, so another element, another render and another request get another. In development (the development checks of the engine) it is frozen, and a function that assigns or deletes a key of it throws, for example:
  `[umber] A style function of "box-root" threw a TypeError of a write into a frozen object: Cannot define property tone, object is not extensible. In development the argument of a style function is frozen: it is one object, the props with the theme, shared by the style functions of the element in a render. Copy the argument before changing it: const own = { ...props }.`
  (the part after `frozen object:` is the language's own message). In production nothing is frozen, and a change to the argument is now seen by the later functions of the same element. What to do: copy the argument before changing it, `const own = { ...props }`, and change the copy. In a warm `renderToString` of the design system's every-component page (82 components), the tarballs of this release packed before and after the change, each page in its own Node 26.4 process, `NODE_ENV=production`, 9 rounds of 300 timed renders after 60, the order of the two alternated: the fastest render took 3.92 ms where it took 4.15, the median 4.45 ms where it took 4.64, and a render allocated 4.7 MB where it allocated 5.0 (the median growth of the heap over 30 batches of 5 renders, after a collection); a second run with the order reversed gave 3.94 against 4.16 ms, 4.50 against 4.65 ms, and the same 4.7 against 5.0 MB. The home page took 67 us where it took 73 (fastest) and allocated 124 KB where it allocated 130. The HTML of both pages is byte for byte the same, in production and in development.
  ([#69](https://github.com/soroush-tech/umber-style/issues/69))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/writing-styles.md#object-styles-and-function-styles)
- **Breaking, in development: the theme that a function of app code gets cannot be written.** It is one object, shared by every render and, on a server, by every request of the process. With the development checks, an assignment, a `delete` or an `Object.defineProperty` into it, at any level, throws, from a style function, a function sheet, a function of `keyframes` or of `globalStyles` (which got the theme with no guard before) and, through the bindings, the function of a theme provider. The message names the path and the function, for example:
  `[umber] theme.space.3 is set by a function of "card-root". The theme is one object, shared by every render and every request, so a change to it reaches all of them: never change it. Build a new object instead, such as [...theme.space].`
  (`is deleted` for a `delete`, `is defined` for `Object.defineProperty`; `{ ...theme.palette, primary: value }` for an object). What to do: never write into the theme; build a new object instead. In production nothing is wrapped and nothing changes. What a function reads is unchanged; in development the guard now wraps plain objects and lists only, so a `Date` or a `Map` of the theme is read with its own methods, and the same part read by the same function is the same object in every render.
  ([#69](https://github.com/soroush-tech/umber-style/issues/69))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/themes.md#the-theme-a-function-gets-is-shared-never-change-it)

### Fixed

- In the browser, a cache given no nonce made its style elements with none, so a page sent under `style-src 'nonce-...'` with a nonce for each request refused every class the browser made (after a client-side navigation, a change of props or state, a component that mounts later, a theme switched at run time): a nonce made for each request cannot be put in a bundle made once. Such a cache now gives the elements it makes for itself, and the element of its live values, the nonce of the page: the `.nonce` of a style element the policy let in, else that of the first script that carries one, read once, when the first element is made. A nonce given to the cache wins; a sheet of `createDomSheet` carries only what it is given; on a page with no nonce, and on a server, nothing changes. A style element the policy refused is never read, and only the engine's own rules go into the element. With the development checks, when the policy refuses the element the cache made, it warns once: that no nonce was found on the page, that the nonce given to the cache is not the page's (it is kept, never replaced), or that the nonce it took is a script's, which a page that gives its scripts and its styles different nonces does not share with its styles.
  ([#71](https://github.com/soroush-tech/umber-style/issues/71))
  [docs](https://github.com/soroush-tech/umber-style/blob/main/docs/server-rendering.md#content-security-policy)

### Packaging

- A new entry, `@umber-style/core/internal`, holds `createThemeGuard`, `callCheckedStyle` and `readPageNonce`: helpers the bindings share, not for apps, with no stability promise between releases.
- No dependency of the family; `csstype` as before.
