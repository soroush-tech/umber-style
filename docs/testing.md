# Testing

After this page you can tell which of three kinds of test a check belongs in, run each one on your machine, and read what the fixture apps do and do not cover.

## The three tiers

| Tier                    | Where                                                        | What runs it                           | What it is for                                                                                   |
| ----------------------- | ------------------------------------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1. Unit and integration | `packages/*/src/*.test.ts(x)`                                | vitest, in jsdom (or Node)             | Rule text, class names, what is inserted where. Fast, and held to 100% coverage                  |
| 2. Real browser         | `packages/core` and `packages/react`, `*.browser.test.ts(x)` | vitest browser mode, headless Chromium | What only a browser's cascade and layout decide: which rule wins, a computed value, a transition |
| 3. End to end           | `e2e/` against the apps in `fixtures/`                       | Playwright Test, headless Chromium     | A whole page from a real build: hydration, extraction, navigation, no-script, size               |

Put a check in the lowest tier that can see the thing. A claim about the text of a rule is tier 1. A claim that one rule beats another, or that a variable resolves to a value, is tier 2. A claim about what a framework does with the engine (what the first HTML holds, whether the page looks the same however you arrive at it) is tier 3.

## Running them

```sh
pnpm test:coverage        # tier 1, every package; fails below 100%
pnpm test:browser         # tier 2, in core and react
pnpm test:e2e             # tier 3, every fixture; builds each one first
E2E_FIXTURE=next-app pnpm test:e2e     # one fixture (a comma-separated list works)
pnpm test:e2e:dev         # tier 3 against development servers; see "Tier 3 in development"
pnpm typecheck            # the type tests of every package, and the budget of the type cost
```

`pnpm typecheck` is not a tier of tests run by a test runner, but it holds the type tests: files that assert what compiles (`expectTypeOf`, `@ts-expect-error`), compiled by each package's `tsconfig*.json`. The typecheck of `@umber-style/react` also runs `scripts/check-type-cost.mjs`, which fails when the types cost the checker more instantiations than a budget on the shapes of a design system (see [How the cost of the types is kept](typed-styles.md#how-the-cost-of-the-types-is-kept)).

Tiers 2 and 3 need Chromium, which Playwright installs once: `pnpm --filter @umber-style/core exec playwright install chromium`. The version of `playwright` in the packages and of `@playwright/test` in `e2e` is the same exact version, so one download serves both. Tier 2 has its own `vitest.browser.config.ts`: `pnpm test` and `pnpm test:coverage` never open a browser. In CI the `browser` job runs tier 2 for `core` and `react`, and the `e2e` job runs one matrix row for each folder of `fixtures/`; a new fixture appears in the matrix with no change to the workflow.

### On each React 19 minor

The packages declare `react` `^19.0.0`, and CI runs the suite on each minor: the `packages`, `build` (with the typecheck), `browser`, `e2e` and `e2e-dev` jobs have one row for each of 19.0, 19.1, 19.2 and 19.3, named with it (`packages (core, react 19.0)`). Each row pins the newest patch of its minor across the workspace before its install, and checks the installed copies after it. Coverage goes to Codecov from the rows on the newest minor only. A machine runs a row the same way:

```sh
node scripts/use-react.mjs 19.0      # or an exact version: 19.0.9
pnpm install --no-frozen-lockfile
node scripts/use-react.mjs --check
# ... the commands above ...
git checkout package.json pnpm-lock.yaml && pnpm install --frozen-lockfile
```

The pin is a root `pnpm.overrides` for `react` and `react-dom`, in the checkout only (`scripts/use-react.md`). `@types/react` stays at the lockfile's version. The App Router fixture runs the React that Next.js bundles whatever is pinned, and its rows say so in their names. A test whose truth depends on the React it runs on reads `version` of `react` and holds the assertions of the other versions as known failures (`nonce.ssr.test.tsx`: React writes a nonce on the style elements it hoists from 19.2 on). `pnpm test:scripts` runs the unit test of the pin's logic with Node's test runner, at 100%.

## Tier 2: real-browser tests

The tests build their CSS with the engine and read `getComputedStyle`. They cover:

- Cascade layers: a style given through `style` beats the component's own property and its `:hover` rule (the pointer is really moved over the element with the browser provider's `userEvent.hover`), unlayered page CSS beats the engine's, a reset in a layer declared before the engine's is beaten by components, and an unlayered reset is not.
- The base class and the props class: a property in both (props wins), a base `:hover` against a plain props property (the base wins while hovered), both defining `:hover` (props wins), and a base `@media` against a plain props property (the props class wins at every width: the difference from one merged class, written down in [Cascade layers and overrides](cascade-layers.md)).
- Theme conditions with themes A, B, A: `when(A)` applies under the first A, not under B, and again under the inner A; `whenScheme` with an explicit scheme and with the emulated system preference (the protocol command `Emulation.setEmulatedMedia`).
- The state keys (`states.browser.test.tsx`): `state('hovered')` while the pointer is over a button, `state('pressed')` while its button is held down (a command of the browser provider that moves the mouse and holds it, which `userEvent` has no call for) and not once it is let go, `state('focused')` for focus reached with the Tab key and not for the focus a click gives, and `state('disabled')` for the `disabled` attribute and for `aria-disabled="true"`, over a hover.
- Registered tokens: `@property` is accepted, a registered colour resolves, and a theme class change under a `transition` runs through values between both ends.
- `alpha()`: both declarations are written and the browser computes the `color-mix()` result.
- Nested themes: three levels each resolve their own values, and `display: contents` wrappers leave the layout of a flex parent's children as it was.
- The development checker and the browser's `CSS.supports`: a property that Chromium does not have (`elevation: 2`, written `elevation:2px`) is dropped from the inserted rule and warned about once, with its class; `-moz-osx-font-smoothing` and `width: '-moz-available'`, which Chromium does not have either, are not; neither is `-moz-box`, the first item of `display: ['-moz-box', 'flex']`, while a last item that Chromium rejects is; and for `elevation: 'var(--anything)'` the warning comes from the property, not the value.

### What a registered token does in a transition

Observed in Chromium 158.0.8127.18 (the build of Playwright 1.65.0), with a `color` transition of two seconds on the element that uses the token, the animation paused at one second:

- A transition on the property that uses the token (`transition: color 2s`) runs after a theme class change, registered or not: the computed colour is halfway between the two ends (`rgb(128, 0, 128)` between blue and red). It runs because the computed colour of the element changes.
- A transition on the token itself (`transition: --umber-palette-primary 2s`, on the element that carries the theme class) runs only when the token is registered. The test sees one transition for the variable, and a colour halfway between the two ends below it. Without `registered` there is no transition and the colour jumps.

## Tier 3: the fixture apps

Each fixture is a private workspace member of `fixtures/`, built with its framework's production build and served as it would be in production. Every one renders the same small app from `fixtures/shared`: three pages (Home, Catalog, Settings), each with components the others do not use, and a promo page whose `Global` outlines the bar of the shell (scenario M), a `Button` with variants, a `Card`, a `Flex` with a gap and direction from props, a nested `ThemeProvider` section, a style that uses a theme breakpoint, and a switch that changes the class on `<html>` and stores the choice, applied by a script in the head before the first paint. The shell renders global base styles with `Global` (a `body` rule with tokens, a rule for `#app-root`, a media query from a breakpoint, two `@font-face` rules of a local font), and a frame switch mounts and unmounts a second `Global` (a top border of `body` in the primary colour), which is on at first. The home page has two animated components: `Spinner` names its `keyframes` inside the `animation` shorthand, `Pulse` in `animationName` with steps that read tokens. They animate `transform` and `outline-color`, which the scenarios do not compare. The bar of the shell of the React fixtures also has a probe of `useId`: an element named by an id of `useId`, under a `Badge` given a plain object in `style` (scenario N). It is in the shell so that it stays mounted from page to page: the class of a plain object goes when no element uses it, which scenario D would count. The Vue fixture has the same, in its own sources.

### Known failures

A test that documents behaviour the engine does not have yet is marked as a known failure through the `known` map of its fixture in `e2e/fixtures.ts` (a scenario of a server-components page under a policy, in `e2e/helpers/cspServer.ts`, through its own `known` field), with a reason that starts with the word KNOWN. Playwright reports it as an expected failure; when it starts to pass the run fails and the mark is removed. There are none today. The groups that were there before are fixed: a class that the browser's cache of the client build writes on a page of server components under a strict policy, new to the document, which went into a style element of its own with no nonce (the style has none, and a nonce for each request cannot be in the bundle), so the policy refused it (scenario (s4) of `cspServer.ts`, a client-side navigation to `/csp-server/badge`, #71: a cache given no nonce now takes the page's for the elements it makes; (s5) and (s6) check a change of state to a new class and a component that only the browser renders, on `/csp-server/interactive`), a client component that reads a token below the provider of the server build, on `/csp-server/badge` (scenario (s3) of `cspServer.ts`, #71: until a style of the client build of the prefix was loaded, that provider had no base theme to merge over, so the component made its class with no value for the token, on the first request of a server, at hydration and after a client-side navigation; the styles of the client build now merge their own base theme under such a theme when they read it; (s3) checks the first load and the class after a navigation, and `next-app.csp-server.spec.ts` checks the first request of a server it starts for the test), the root rule of a registry element that streams into the body after the browser's cache declared its root theme, which undid a theme switched while the page streamed until the next declaration (`registry-late-root`: the cache removes it as the element arrives, and the scenario switches the theme before the late chunk arrives and checks that the page stays in it), what a server component reads of the theme differing between a full render and a partial render (`partial-root-theme`: `useTheme()` of a server component, and the theme a function theme gets, are now the base theme in every render), a page carrying the rules of other pages (`extractPageStyles` reads the page), a client component unstyled in the first HTML (the client build renders style elements on a server), the dark theme class of the browser lacking variables that server components use (the browser reads the rules of the page and completes the classes it made), a page carrying the global rules of another page that the same server rendered (the markup of a page names the sets of its `Global`), and the global rule of a server component's `Global` staying after its page was left (a client component that it renders lets the browser's cache release it).

`findMissingStyles` is the checker of `@umber-style/core`, the one that the development mode runs. The end-to-end helper carries no copy of it: it sends the compiled text of that file into the page.

### The development checker

With `hasDevChecks` (on in development where there is a `document`, see [Options](options.md)) the cache checks the page after start-up, when it inserts rules and when style elements arrive, throttled, and warns once for each message, with the prefix of the engine: `[umber] ...`. It reports:

- An element with a class of the engine that no rule names (`findMissingStyles`).
- A variable of the engine that a rule matching the element uses without a fallback, and that has no value on the element.
- A global rule for `html`, `body` or `:root` whose variables have no value there: no outermost provider declares its theme on `:root`, and no theme class is on `<html>`.
- A declaration of a rule that the cache inserted, or of a global rule it wrote, that the browser does not support, asked with `CSS.supports`: `[umber] the class umber-x1 declares elevation:2px, which this browser does not support`. A class with a label is named with its component: `[umber] the class umber-Button-root-x1 of "Button-root" declares border-color:light, which this browser does not support` (checked in Chromium). A global rule is named by its selector, a step of `@keyframes` by the name of the animation.

The caches of one prefix that write into one page (the engine's own cache, made by `configure`, and an app's `createCache({ key })` under a `CacheProvider`) share the check of that page: the page is looked at once for all of them, the rules of each are asked about with the labels of its own classes, and each message is given once, not once for each cache (`cache.pageCheck.test.ts`). A cache made after another one of the prefix still checks the page, and does not repeat what was told on it.

Two more checks need no page and no browser, so they run wherever the checks are on, in jsdom and on a server too:

- A value that no CSS property takes, whatever the property, which the engine can tell by itself: `true`, a function, a number that is not finite (`NaN`, `Infinity`), and an object in a list of values: `[umber] the class umber-wide-root-x1 of "wide-root" declares "width" as true, which is never a CSS value: give a string or a number.` A word such as `light` is not one of them: whether a property takes it is for the browser to say, through `CSS.supports` above.
- What a style function returns that is not a style (a string, a number, `true`, a function): `[umber] A style function of "Odd" returned 1, which is not a style: ...`. The engine checks it, and leaves out what it warned about, so the cache does not warn about it again.
- A `NaN` value is warned about with a hint: in a style function a token is a reference, so `theme.space[2] * 2` is `NaN`; use `multiply()` or `calc()`, a raw or inline mode, or `useTheme()`.
- A value given to `css` of the cache that is not a style, a class name or an entry (`cache.css(5)`, `true`, a function), which is left out: `[umber] css() was given 5, which is not a style: it is left out. ...`, with `for "<label>"` when the class has a label.
- An `@scheme` key that names neither `light` nor `dark` (`'@scheme blue'`), which is written as an at-rule the browser drops.
- A reference followed by a unit that value repair leaves as it is (see [Tokens](tokens.md#string-forms-of-token-maths)).
- A declaration of a `css()` value given to `Global` that is outside every selector, which a global rule leaves out (see [Animations and global styles](animations-and-global-styles.md#what-styles-takes)).
- A rule that the browser rejects when the cache's own sheet writes it with `insertRule`: `[umber] the browser rejected the rule of .a (<the browser's message>): it is left out.`
- With the engine's checks: a token whose value is a CSS-wide keyword (see [Tokens](tokens.md#a-token-whose-value-is-a-css-wide-keyword)); a style function of a server component that runs with no base theme and no provider yet, which reads an empty theme, told once for each component before it runs (see [Server rendering](server-rendering.md#limits)); a path of `modes`, `registered` or `alwaysDeclare` that matches no key of the theme, when the tokens are made; an option of the cache column given to an engine together with a `cache` (see [The cache and server packages](cache-and-server.md#cacheprovider-a-cache-for-a-subtree)); and a read of the theme view in a style function with a key that is a token reference (`theme.space[theme.layout.margin]`), which gives `undefined`: `[umber] A style function of "Box" reads theme.space[var(--umber-layout-margin)]: ... Give "layout.margin" a raw mode (modes: { 'layout.margin': 'raw' }), or read the real value from useTheme().` For that one the view is wrapped in a `Proxy` while the checks are on; without them a style function gets the view itself (`referenceKeys.test.ts` checks that it is the same object).

### The checks in a test run

The checks are off by default in a test run (`process.env.NODE_ENV` is `test`, not `development`). `hasDevChecks: true` turns them on; give it where the style is configured for the tests, for example in a setup file that vitest runs before each test file (`setupFiles` in `vitest.config.ts`). From `packages/react/src/devChecks.test.tsx`:

```ts
import { configure } from '@umber-style/react'

configure({ prefix: 'app', theme, hasDevChecks: true })
```

A style function that returns `3` and a style with `width: true` each warn once then. In jsdom `CSS.supports` is not asked (jsdom answers from a table of its own), so `borderColor: 'light'` says nothing there; it does in a browser. The page check (`findMissingStyles`) runs in jsdom too, after its wait of 250 milliseconds. The warnings of React Native (a dropped web-only key, a value it does not convert) do not read `hasDevChecks`: they are on wherever `process.env.NODE_ENV` is not `production`, so a test run has them already.

What it does not report:

- A property with a vendor prefix (`-webkit-`, `-moz-`, `-ms-`, `-o-`): a declaration written for another browser is not a mistake. A custom property (`--x`) takes any value.
- A value that starts with a vendor prefix, a keyword or a function (`width: '-moz-available'`, `-webkit-linear-gradient(...)`), with or without `!important`: written for another browser too.
- The earlier items of a fallback list: only the last declaration of a property in a rule is asked about.
- The value of a declaration that holds `var(`: such a value is valid until it is used, so the browser is asked whether it knows the property at all.
- Anything about declarations where `CSS.supports` is missing, throws, or does not answer like a browser: a server, and jsdom, which answers from a table of its own.
- The descriptors of `@property` and `@font-face`, and `!important`, which is left out of the question.
- A rule that the browser drops as a whole when it parses the text of a style element (a selector or an at-rule it does not know, such as `@scope` in a browser without it): written as text, nothing tells the cache. Written with `insertRule` the browser throws, and the cache warns (above). Its declarations are still asked about.
- A token reference used as a key of an object that is not the theme view (`sizes[theme.typography.h1.fontSize]` with a `sizes` of your own): only the view is watched.
- The rules that reach the page in style elements (written by a server, or rendered by React and hoisted into the head): the cache does not insert them, so they are not asked about.

## Tier 3 in development

The scenarios above run each fixture as a production build. The development tier starts three of them with their development servers instead: `vike-ssg` (Vike's development server), `next-app` (`next dev`, App Router) and `spa` (the Vite development server). The fixtures that have one say so with a `devPort` in `e2e/fixtures.ts` (the production port plus 100), and a `dev` script in their `package.json`. The specs are in `e2e/dev-tests/`, and the configuration is `e2e/playwright.dev.config.ts`, so `pnpm test:e2e` is unchanged and does not run them.

```sh
pnpm test:e2e:dev                      # the three development servers
E2E_FIXTURE=spa pnpm test:e2e:dev      # one fixture (a comma-separated list works)
```

The tier runs one test at a time, because the hot replacement tests write files that all three fixtures share, and a global setup loads every page of every server once first, so that a test meets a server that has compiled and optimized what it needs. Every test fails on a console error, an uncaught error, any message that mentions hydration, and any warning of the engine's own development checker (`[umber] ...`).

## What is not covered

- React Native on a device or a simulator. The binding is tested in unit tests with a stand-in for the platform import; its `Pressable` has the contract of the platform's `Pressable.js` (a state of its own, set on a press only when `style` or `children` is a function, which it calls with `{ pressed }`), not Pressability's timing.
- Browsers without cascade layers, `@scope`, `@property` or `color-mix()`. Only Chromium runs; the fallbacks are tested as text.
- Firefox and WebKit. Playwright can drive them, no project does.
- A bundler other than Vite and Turbopack. Next.js was built with the default bundler of its current major.
- Lighthouse in CI is a generous guard (score above 0.5, blocking time under a second, transfer under a megabyte). It is not a performance budget.

## Limits

- The fixtures hold the same few components. A defect that needs another shape of style may not show.
- The React rows run the newest patch of each minor, resolved when the job runs: an older patch of a minor is not run, and a new patch can make a row fail on a pull request that changed nothing. The App Router fixture never runs the React an app installs, on any row.
- Scenario G runs several times at once with the other scenarios on one machine. Its numbers are for comparison between fixtures on the same run, not absolute.
- The text of a rule that a browser cache inserted after load is not seen by the rule usage tracking: scenario E does not apply to a client-only app.
- The class on `<html>` is switched by script. A page with scripting disabled stays in the scheme that the server chose.
- The development checker's question to `CSS.supports` is tested in Chromium only: what Firefox or WebKit would reject is not observed.
- The check of values that no property takes reads the styles of classes and of global styles. The steps of a `keyframes` and what a style function hands on inside a nested object are checked only as part of the class they make.
- In a test run the DOM sheet writes its rules as text, as in development: each rule in a `<style data-style="<prefix>">` element of its own, so a test that reads the CSS joins the text, or the `sheet.cssRules`, of every element of the prefix, in document order. What jsdom parsed is what it parsed from that text. A test that needs the way of production gives `speedy: true`, as does a large suite that never reads the CSS text. The unit tests of the core run the tests of what a cache writes to a document twice, once in each way (the `text` and `insertRule` projects of `packages/core/vitest.config.ts`).
