# Browser and platform support

After this page you can tell which browser features the engine's output needs, what happens in a browser that lacks one, and which versions of the tools the packages were built against.

**Browser version numbers are not stated here.** The repository has no test that runs a browser, so no minimum version was checked. Each row names the feature that is required, and the version that first supports it is to be confirmed against a browser compatibility source before it is published.

## What the output needs

| Feature                                        | Used for                                                     | When it is written                               | In a browser without it                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| CSS custom properties                          | Every token                                                  | Always                                           | The engine does not work                                                                     |
| Cascade layers (`@layer`)                      | The four layers                                              | Unless `hasLayers: false`                        | Every rule is dropped. With `hasLayers: false` nothing is written in a layer                 |
| `display: contents`                            | The `<prefix>-scope` wrapper of a provider                   | Always, with a provider that renders a wrapper   | The wrapper takes part in layout                                                             |
| `color-mix()`                                  | `alpha()` with an opacity between 0 and 1                    | With `alpha()`, after the fallback               | The declaration is ignored; the fallback declaration before it applies (`hasColorFallbacks`) |
| `@property`                                    | Registered tokens                                            | Only for tokens you register                     | The rule is ignored: the token works and does not animate                                    |
| `@keyframes`, CSS animations                   | `keyframes`                                                  | Only when a style or a global rule names one     | The animation does not run                                                                   |
| `@scope`                                       | `when()` and `whenScheme()`                                  | Only when you use them, unless `hasScope: false` | Those rules are dropped, and the style falls back to the base style                          |
| `:where()`, `prefers-color-scheme` media query | The guard of `whenScheme` for the system preference          | Only with `whenScheme`                           | The rule is dropped                                                                          |
| Media query range syntax (`width >= 600px`)    | The output of `@soroush.tech/styled-system` responsive props | Only with that package                           | The media rule is dropped. This is that package's output, not the engine's                   |

A rule that a browser rejects is skipped when it is inserted (`createDomSheet` catches the error), and the rest of the sheet still loads. For a page rendered on the server, the rules are text in a `<style>` element, and the browser parses them, ignoring what it does not know.

## Vendor-prefixed declarations

A few declarations still need a prefixed form in a browser the engine supports. For each of them the engine writes the prefixed form first, then the standard declaration, in the same rule: `{ userSelect: 'none' }` is written `-webkit-user-select:none;user-select:none;`. The table is fixed (`PREFIXED_FORMS` in `packages/core/src/vendorPrefixes.ts`); it is not an option to extend.

The supported browsers, for this table: the releases of the last two years of Chrome, Edge, Firefox and Safari, iOS Safari included. The page above states no versions, so this is the range the table was checked against: on 2026-11-22, Chrome and Edge 132 and later, Firefox 133 and later, Safari and iOS Safari 18.2 and later.

What the engine does:

- It writes the forms wherever declarations are written: classes, sheet entries and `css()` values (and their `styles` text), global rules (and the `styles` text of a `globalStyles` handle), the steps of `keyframes`, the classes and global rules of `@umber-style/css`, and so the CSS that a server extracts.
- A form that the style declares itself is not written again, and the declarations stay in the order you wrote them: `{ WebkitUserSelect: 'none', userSelect: 'none' }` gets nothing more, and `{ width: ['-webkit-fill-available', 'stretch'] }` gets only `-moz-available` in front, which it lacks.
- An item of a fallback list gets its form too, the forms of the list before the list: `{ userSelect: ['text', 'all'] }` is `-webkit-user-select:text;-webkit-user-select:all;user-select:text;user-select:all;`.
- A class is named from the style without the forms, so its name is the same with the option or without it (`vendorPrefixes.test.ts`). The id of a set of global rules is a hash of the rules written, forms included, and the name of an animation is made from its steps without them.
- `hasVendorPrefixes: false` (an option of the engine, `createStyle`, `configure`, the cache, `createCache` of `@umber-style/cache` and `createInstance` of `@umber-style/css`) writes the standard declarations only, the output from before. It is part of the stamp of options that a server page carries, written only when it is off (`w=0`), so the stamp of a page with the default is the text it was before. Under a cache it was given (a `CacheProvider`), an engine keeps the value it was given, as it keeps `hasValueRepair`.
- The development checker never reports a prefixed property (it asks only about standard ones), and it does not report a standard declaration that the browser does not support when the same rule has a prefixed form of it that the browser supports (`user-select` in Safari).
- The cost: one lookup in a `Map` by the property name for each declaration of a class that is written, none for a class that is already there.

## Floors

- **With the defaults**, the floor is a browser that supports custom properties, cascade layers and `display: contents`: the features that have no fallback. The one of them that arrived last decides the floor; which one that is, and its version, is to be confirmed.
- **With `hasLayers: false`**, the floor is a browser with custom properties and `display: contents`, and colours degrade to their fallbacks. That claim rests on the specifications and on the output of the engine. It was not run in an old browser.
- Without `color-mix()` the colour of an `alpha()` is its fallback: the literal at that opacity as `rgba()` if the engine can read it, otherwise the colour at full opacity.

## Limits

- The table of prefixed forms rests on the support data cited above, read on 2026-11-22: no Safari, Firefox or Edge was run. The browser tier (`vendorPrefixes.browser.test.ts`) runs Chromium only, where `-webkit-user-select`, `-webkit-print-color-adjust` and `-webkit-box-decoration-break` compute to the value that was set, and `width: stretch` written after its prefixed values computes to the width of its container. A table is as current as the day it was checked: a form that browsers stop needing stays written, harmless, until the table is checked again.
- With the forms of `stretch`, the development checker asks about the last declaration of the property, `stretch`: in a Chrome before 138 it reports `width:stretch` although `-webkit-fill-available` before it applies.
- Two engines over one cache with different `hasVendorPrefixes` write the same class name for the same style; the rule of the one that writes it first is the one in the sheet.

- No browser was used. Everything in the first table is the engine's output plus knowledge of the CSS features, not an observed result.
- jsdom was used for DOM tests. It evaluates `@scope` and `@layer` and computes custom properties, but it is not a browser and runs no transitions.
